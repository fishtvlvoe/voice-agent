Voice Agent 架構盤點

從舊系統抽出的語音收單功能，整理給接手的 Agent 看資料庫、LIFF、LINE 怎麼串起來。內文已避開組織名稱，只保留技術結構。

1整體流程

使用者在 LINE 對話框打開連結
→
LIFF 語音頁面（網頁）
→
跟後端換一組短效期語音金鑰
→
瀏覽器直連語音 AI 即時通話
語音 AI 判斷欄位填完
→
呼叫後端「送出」API
→
寫回資料庫 / 推播確認
語音 AI 引擎：xAI Realtime API。前端瀏覽器直接跟語音 AI 對話，後端只負責「發語音通行證」跟「收最終結果」，通話過程本身不經過後端。

2LIFF 前端怎麼架在 LINE 裡

  • LINE 官方帳號的選單／訊息裡放一個 LIFF 網址，點開會在 LINE App 內建瀏覽器打開一個網頁
  • 網頁載入時用 LIFF SDK 拿到這個使用者的 lineUserId 跟一個一次性 idToken（證明「這真的是這個人在操作」）
  • 網頁前端檔案：語音收單頁面本體 + 共用前端邏輯 + 表單欄位定義（放在前端也放在後端，兩邊要對齊）
  • 每一支後端 API 都要求帶 lineUserId + idToken，後端會拿 idToken 去跟 LINE 官方驗證「這組 token 真的對應這個 lineUserId」，防止有人冒充別人的身分打 API

3後端 API 路由

路徑做什麼狀態
POST /api/voice-session/token 驗證身分 → 跟語音 AI 服務商換一組 15 分鐘的通行證，回傳給前端。同時把「這個人的聯絡人別名清單」「上次記住的常用資料」一起塞給前端，讓語音 AI 開場就有上下文 保留
POST /api/voice-intake/submit 語音 AI 判斷資料收集完整後呼叫，把結構化欄位送回來 內部轉發到別的服務，要改成直接寫自己的資料庫
POST /api/voice-intake/remember 使用者說「幫我記住電話/信箱/地址」時呼叫，白名單只允許這三種欄位，單筆長度上限 500 字 保留
POST /api/internal/voice-intake 備用路徑，設計給語音 AI 服務商後台直連（不經過 LIFF 前端），目前沒在正式使用 可保留，設計備用

4資料庫（原本用 Cloudflare D1，SQLite 相容）

資料表欄位用途
line_user_memory line_user_id, field_key, field_value, updated_at 記住使用者的電話/信箱/地址，下次開口說「用我的電話」直接代入
line_user_profiles line_user_id, last_known_display_name, last_seen_at 使用者基本資料快取
member_aliases（要重新命名） 姓名清單 語音辨識常把人名聽成同音錯字，先把「可能會被提到的人名清單」餵給語音 AI 校正。獨立系統要換成通用的「聯絡人／常用名單」概念，不綁特定組織的會員名冊
另外有一個 KV（key-value 暫存），存 voice-intake:active-user，只在上面「備用路徑」那條線用，記錄「目前是哪個使用者在講話」，處理完就刪除。

5語音表單設計（4 種表單類型，用 function calling）

  • 語音 AI 用三個「工具」跟後端互動：finish_current_entry（存這一筆）、submit_voice_intake（全部送出）、remember_info（記住聯絡資料）
  • 每種表單類型定義自己的必填欄位（例如：對象姓名、日期、地點、聯絡電話等），AI 靠使用者講話內容自動判斷是哪一種表單，不用使用者自己選
  • 支援一次講多筆（例如連續講好幾位聯絡人），排隊依序處理
  • 系統會給 AI 一段「人設指令」，規定用繁體中文對話、一次只問一題、欄位確認方式、不能自己編日期等規則
這 4 種表單類型本身是原系統的業務模板（聯誼會的商務往來紀錄），獨立系統要不要保留一樣的表單種類、或改成通用聯絡表單，是接手 Agent 要決定的設計題，這份盤點不含這個決策。

6外部依賴清單

依賴用途
xAI Realtime API語音對話引擎本體，前端瀏覽器直連，用短效期 client secret 授權
LINE LIFF SDK + LINE 身分驗證取得使用者身分、在 LINE App 內嵌瀏覽器打開網頁
原本的訊息推播服務（要拔掉）語音收單完成後推播確認訊息，這條線要換成獨立系統自己的通知方式，或先只落地資料庫

7接手前要決定的事

  • 語音收單完成後的資料要存哪裡（目前是轉發給別的服務，這條線需要換掉）
  • 「聯絡人別名清單」這個概念要不要保留，資料從哪裡來
  • 4 種表單類型要原封不動，還是簡化成通用一種
  • 通知使用者「已收到」的方式（原本靠 LINE 推播，獨立系統要另外設計）
