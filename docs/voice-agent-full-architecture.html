Voice Agent 完整模組架構

回答：WeKnora 能補什麼、原架構缺什麼、完整模組怎麼分

1WeKnora 能做這件事嗎？

WeKnora 是一套 RAG 知識庫框架：文件解析 → 切塊 → embedding → BM25 + 向量混合搜尋 → 排序融合 → 組成 Context 給 LLM 回答，並附上引用來源。它解決的是「問企業知識庫問題時，答案要有根據，不能瞎編」這一件事。

它不解決的兩件事，剛好就是你問的兩個缺口：
  • 資料清洗：WeKnora 假設進來的是「已經是文字的文件」（PDF、Word、網頁）。語音收單的原始輸入是「語音辨識後的口語文字」，充滿同音錯字、不完整句子、講一半改口——這一段清洗，WeKnora 完全沒有，要另外做
  • 跨通路使用：WeKnora 只管「知識庫怎麼被查」，不管「使用者從哪裡進來」。LINE、網頁、App 是三種不同的「入口」，這是另一層要設計
結論：WeKnora 適合放進架構「當一個模組」——回答一般性問題用的知識庫引擎。它不能取代語音收單本身的資料清洗跟多通路，那兩塊要另外建。

2原本架構的兩個洞

洞現況後果
沒有資料清洗層 語音辨識出來的欄位直接被當成「使用者確認過的正確資料」寫進資料庫，只做繁簡轉換跟白名單檢查 同音錯字、地址格式不一致、電話格式不一致，全部原樣進資料庫，之後要用這批資料做任何分析或比對都會失準
綁死 LINE 一種入口 身分驗證只認 LINE idToken，結果送出去也只走 LINE 的服務綁定；表單頁面本身也是 LIFF（LINE 內嵌瀏覽器專用） 使用者不用 LINE 就完全用不了；換一個通路（獨立網頁、App、電話）等於要重寫一整套

4資料清洗層具體要做什麼

髒資料類型清洗方式
人名同音錯字比對「常用聯絡人清單」做校正（原本 member_aliases 那招，通用化保留）
電話格式不一正規化成固定格式（去除空格/破折號，統一國碼或不加國碼的規則）
地址格式不一基本結構化（縣市/區/路），至少能做去重比對
日期口語轉換「下禮拜三」「後天」這類相對日期，語音當下已換算成 YYYY-MM-DD，清洗層只需再驗證格式合法
金額/數字單位「三萬五」「35000」統一轉成數字，防止漏零多零
Email 格式基本格式驗證（含 @、網域），不合法退回請使用者口頭重講
原始辨識結果跟清洗後結果都要留底，之後才有辦法回頭檢查「清洗規則是不是洗錯了」。

5多通路怎麼做，不用重寫

  • 核心 API（收單、記憶、驗證）維持一套，不要為每個入口各寫一份
  • 身分層抽成「介面」：LINE 用 idToken，網頁用一般帳密或簡訊驗證，都轉成同一種內部使用者代碼，後面的邏輯完全不用管「這人從哪裡來」
  • 前端頁面可以有多份（LIFF 版、獨立網頁版），但呼叫的是同一組後端 API
  • 通知回傳層依「使用者是從哪個入口登記的」決定推播管道，而不是寫死推 LINE

6RAG 知識庫接在哪一層

WeKnora 不是取代語音收單，是加一條新能力：使用者講話時如果問的是「規則是什麼」「這個要準備什麼」這類開放式問題（不是在填表單），語音助理可以查 WeKnora 知識庫回答，回答時附引用來源，不是瞎猜。這跟收單流程是平行的兩件事，共用同一個語音對話引擎、同一個身分層，但走不同的資料庫。
